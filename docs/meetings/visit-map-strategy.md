# Visit 지도 제공 방식 회의

## 주제

Visit 페이지에서 매장 위치를 보여줄 때 정적 지도 미리보기와 Naver Map SDK 기반 동적 지도 중 어떤 방식을 우선할지 결정

## 참여 직군

FE, PD, PM

## 확인된 사실

- 현재 Visit 페이지는 Server Component이며 지도 SDK 의존성과 공식 좌표가 없습니다.
- 현재 저장소에는 네이버 플레이스 링크가 있지만, 공식 좌표와 리뷰 직접 URL은 확인되지 않았습니다.
- 주소, 길찾기, 리뷰는 서로 다른 사용자 행동입니다. 페이지 안 지도는 위치와 주변 맥락 확인을 돕고, 외부 지도는 실제 길찾기를 시작하게 하며, 리뷰는 방문 결정을 보조합니다.
- 네이버의 최신 정적 지도 제공 여부, 인증 방식, 가격·쿼터, 캐시·저장 정책, SDK·API 약관은 이번 회의에서 확인하지 않았습니다.

## 사용자 문제와 목표

- 방문자는 다른 페이지로 이동하기 전에 매장이 어디에 있고 주변과 어떤 관계인지 빠르게 파악할 수 있어야 합니다.
- 위치를 확인한 뒤에는 길찾기와 방문자 리뷰 중 원하는 다음 행동을 명확하게 선택할 수 있어야 합니다.
- 모바일에서 지도 조작이 스크롤을 방해하거나, 지도 로딩 실패 때문에 주소와 핵심 CTA를 잃어서는 안 됩니다.
- 목표는 페이지 내 위치 확인 편의 향상입니다. 외부 이탈 감소나 방문 전환 상승은 아직 확인되지 않은 가설이며 배포 후 측정해야 합니다.

## 결정 사항

현재 단계에서는 **사용 조건이 확인된 공식 정적 지도 미리보기**를 우선합니다. Naver Map SDK 기반 동적 지도는 실제 상호작용 수요가 확인될 때 도입을 재검토합니다.

- Address 영역의 순서는 `Find ROUTINE → 주소 → 정적 지도 → 네이버 지도에서 길찾기 → 네이버에서 방문자 리뷰 보기`로 구성합니다.
- 지도는 페이지 안에서 위치와 주변 맥락을 확인하는 보조 정보로 사용합니다.
- `네이버 지도에서 길찾기`를 primary CTA로 유지하고, `네이버에서 방문자 리뷰 보기`를 secondary CTA로 추가합니다. 지도 도입을 이유로 길찾기를 리뷰 링크로 대체하지 않습니다.
- 지도 자체를 선택하면 네이버 지도 또는 플레이스의 확인된 공식 URL로 이동하게 하되, 별도의 텍스트 CTA도 유지합니다.
- 공식 정적 지도 방식의 사용 조건을 확인하기 전에는 임의 지도 캡처, 추정 좌표 또는 무단 저장 이미지를 사용하지 않습니다.
- 공식 정적 API가 비밀 인증 정보를 요구한다면 브라우저에 노출하지 않고 최소 Route Handler를 검토합니다. 캐시·저장 여부는 확인된 약관 범위 안에서만 결정합니다.

## 결정 근거

- 정적 미리보기만으로도 현재 핵심 요구인 페이지 내 위치 확인을 충족할 수 있습니다.
- JavaScript SDK, 지도 타일 초기화와 별도 Client Component 없이 현재 Server Component 구조를 유지할 가능성이 높습니다.
- 고정된 크기의 이미지는 layout shift를 예방하기 쉽고, 지연 로딩과 오류 fallback도 단순합니다.
- 모바일 스크롤 중 확대·이동 gesture가 충돌하지 않아 핵심 정보 탐색이 안정적입니다.
- 동적 지도는 확대·이동 같은 기능을 제공하지만 현재 그 기능이 필요하다는 사용자 근거가 없고, 초기 로딩·접근성·오류 처리·운영 설정의 범위를 늘립니다.

## 정적·동적 방식 비교

| 판단 기준 | 공식 정적 지도 미리보기 | Naver Map SDK 동적 지도 |
| --- | --- | --- |
| 현재 사용자 목표 | 위치와 주변 맥락 확인에 충분 | 확대·이동 등 페이지 내 탐색까지 가능 |
| 구현 범위 | 이미지 표시와 fallback 중심 | Client Component, SDK 로딩·초기화와 상태 처리 필요 |
| 성능 | JS·타일 초기화가 없어 상대적으로 단순 | SDK와 타일 로딩 비용이 추가될 수 있음 |
| 모바일 사용성 | 스크롤 gesture와 충돌이 적음 | 지도 gesture와 페이지 스크롤 충돌을 설계·검증해야 함 |
| 접근성 | 대체 텍스트, 주소와 별도 CTA로 단순하게 보완 가능 | 키보드 조작, 초점 이동, 비시각적 대체 경로를 추가 검증해야 함 |
| 실패 대응 | 주소와 CTA를 그대로 유지하는 fallback이 단순 | SDK·인증·네트워크·초기화 오류별 fallback이 필요 |
| 운영 조건 | 정적 API의 인증, 가격·쿼터, 캐시·저장 정책 확인 필요 | client ID, 허용 도메인, 가격·쿼터와 SDK 약관 확인 필요 |
| 현재 판단 | 우선 도입 | 승격 조건 충족 시 재검토 |

## 화면 원칙

- 데스크톱 지도는 `16:9`, 최대 높이 `400–420px` 범위에서 Address 영역 너비에 맞춥니다.
- 모바일 지도는 `4:3` 비율로 제공하고 페이지 좌우 여백을 유지합니다.
- 로딩 전후 크기를 고정하고 지연 로딩합니다.
- 지도 색상을 강제로 흑백화하지 않으며, 기존 Paper 배경과 구분되는 중립 테두리를 사용합니다.
- 지도 이미지가 로딩되지 않아도 주소, 길찾기와 리뷰 CTA는 그대로 표시합니다.
- 지도에는 매장명과 위치를 설명하는 대체 텍스트를 제공하고, 정확한 이동 행동은 텍스트 CTA로도 수행할 수 있게 합니다.

## 담당자별 후속 작업

- PM
  - 운영자와 함께 공식 주소에 대응하는 정확한 좌표와 리뷰 직접 URL을 확인합니다.
  - `길찾기`, `방문자 리뷰 보기`의 목적과 문구가 실제 연결 대상과 일치하는지 확인합니다.
  - 배포 전후 지도 노출 대비 길찾기·리뷰 CTA 선택률과 Visit 페이지 이탈률을 비교할 수 있는 측정 정의를 작성합니다. 분석 수단이 없으면 우선 이벤트 정의만 남깁니다.
- FE
  - 네이버 공식 문서에서 정적 지도 제공 여부, 인증 정보 노출 조건, 가격·쿼터, 캐시·저장 정책과 도메인 제한을 확인합니다.
  - 확인된 공식 방식으로 최소 구현안을 산정하고, 비밀 인증이 필요할 때만 Route Handler를 사용합니다.
  - 고정 비율, 지연 로딩, 오류 fallback, 키보드 접근과 반응형 화면을 검증합니다.
- PD
  - 주소, 지도, primary 길찾기 CTA와 secondary 리뷰 CTA의 시각적 위계와 간격을 검수합니다.
  - 데스크톱 `16:9`, 모바일 `4:3` 지도 크기가 주변 콘텐츠를 압도하지 않는지 확인합니다.
  - 지도 로딩·실패 상태와 모바일 스크롤 흐름을 검수합니다.

## 완료 기준

- 공식 자료로 확인된 주소와 좌표만 지도에 사용합니다.
- 공식적으로 허용된 정적 지도 제공 방식과 인증·가격·쿼터·캐시·저장 조건을 확인하고 준수합니다.
- 지도는 데스크톱과 모바일에서 합의한 비율을 유지하며 로딩 전후 layout shift를 유발하지 않습니다.
- 지도 로딩 실패 또는 외부 서비스 오류에도 주소, 길찾기와 리뷰 CTA를 사용할 수 있습니다.
- `네이버 지도에서 길찾기`와 `네이버에서 방문자 리뷰 보기`가 확인된 각 목적지로 연결됩니다.
- pointer와 keyboard로 지도 링크와 두 CTA를 사용할 수 있고 명확한 `focus-visible`을 제공합니다.
- 모바일에서 가로 overflow가 없고 지도가 페이지 스크롤을 방해하지 않습니다.
- 측정이 가능한 경우 지도 노출, 길찾기 선택, 리뷰 선택과 Visit 이탈 이벤트가 구분됩니다.

## 동적 지도로 승격할 조건

다음 중 하나 이상의 수요가 실제 사용자 행동, 문의 또는 운영 요구로 확인되고 정적 미리보기와 외부 길찾기로 해결되지 않을 때 Naver Map SDK 도입을 재검토합니다.

- 사용자가 페이지 안에서 확대·이동하며 주변 도로, 역 또는 랜드마크를 탐색해야 합니다.
- 여러 매장이나 여러 위치를 비교·선택해야 합니다.
- 지도 위에 복수 marker, 위치별 상태 또는 상호작용 정보가 필요합니다.
- 정적 지도 이후에도 위치 이해 실패나 잘못된 길찾기 문의가 반복됩니다.

승격 시에는 페이지 전체를 Client Component로 바꾸지 않고 지도만 최소 Client Component로 격리합니다. viewport 진입 또는 사용자 활성화 전까지 SDK 로딩을 지연하고, SDK 실패 시 주소·정적 대체 화면·길찾기 CTA를 유지합니다.

## 측정 방법

- 가설: 페이지 안 지도 미리보기가 방문자의 위치 이해를 도와 불필요한 즉시 이탈을 줄이고 길찾기 또는 리뷰 행동으로 이어지게 합니다.
- 우선 지표: 지도 노출 사용자 중 길찾기 CTA 선택률, 리뷰 CTA 선택률
- 보조 지표: Visit 페이지 이탈률, 지도 링크 선택률, Contact 또는 방문 관련 문의 변화
- 가드레일: 모바일 성능 지표, 지도 로딩 실패율, layout shift, 키보드 접근 실패와 스크롤 방해 이슈
- 분석 데이터와 이벤트 수집 방식이 확정되기 전에는 개선 효과를 단정하지 않습니다.

## 미결 질문

- Cafe Routine의 공식 주소에 대응하는 정확한 좌표는 무엇이며 누가 최종 승인합니까?
- 방문자 리뷰로 직접 연결되는 공식 네이버 URL은 무엇입니까?
- 네이버가 현재 제공하는 공식 정적 지도 방식과 인증 조건은 무엇입니까?
- 정적 지도와 SDK 각각의 가격·쿼터, 도메인 제한, 캐시·저장 및 표시 약관은 무엇입니까?
- 정적 API가 비밀 인증을 요구할 경우 Route Handler 응답을 어느 범위까지 캐시할 수 있습니까?
- 배포 전후 행동을 비교할 기존 분석 도구와 기준 데이터가 있습니까?

이 문서는 공식 좌표·URL과 네이버 지도 제공 조건을 확인한 뒤 같은 주제의 후속 회의에서 갱신합니다.
